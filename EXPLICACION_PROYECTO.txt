1. ¿QUÉ ES PIPEX?
================================================================================

Pipex es un proyecto de 42 que simula el comportamiento de los pipes en shell.
El objetivo es recrear la funcionalidad del operador pipe (|) en bash.

EJEMPLO EN BASH:
    < file1 cmd1 | cmd2 > file2

EQUIVALENTE EN PIPEX:
    ./pipex file1 "cmd1" "cmd2" file2

El programa debe:
- Leer del archivo file1
- Ejecutar cmd1 con file1 como entrada
- Pasar la salida de cmd1 como entrada a cmd2
- Escribir la salida de cmd2 en file2

================================================================================
2. PARTE MANDATORIA
================================================================================

ARCHIVOS:
- main.c              : Punto de entrada del programa
- child_process.c     : Manejo de procesos hijos y ejecución de comandos
- find_executable.c   : Búsqueda de ejecutables en PATH
- pipex.h             : Header con declaraciones

REQUISITOS:
- Exactamente 4 argumentos: file1, cmd1, cmd2, file2
- Usar exactamente 2 comandos
- Manejar errores correctamente
- Sin memory leaks
- Cumplir norminette

COMPILACIÓN:
    make

USO:
    ./pipex infile "ls -l" "wc -l" outfile
    
    Equivalente a: < infile ls -l | wc -l > outfile

- pipex_bonus.h         : Header del bonus

FUNCIONALIDADES BONUS:

A) MÚLTIPLES PIPES:
   ./pipex file1 cmd1 cmd2 cmd3 ... cmdn file2
   
   Ejemplo:
   ./pipex infile "ls -l" "grep txt" "wc -l" outfile
   
   Equivalente a:
   < infile ls -l | grep txt | wc -l > outfile

B) HERE_DOC:
   ./pipex here_doc LIMITER cmd1 cmd2 file
   
   Ejemplo:
   ./pipex here_doc EOF "grep hello" "wc -l" outfile
   
   Equivalente a:
   cmd1 << LIMITER | cmd2 >> file
   
   El programa leerá de stdin hasta encontrar LIMITER, luego
   ejecutará los comandos y añadirá (append) al archivo de salida.

COMPILACIÓN:
    make bonus

4. EXPLICACIÓN DE FUNCIONES
================================================================================

---------------- PARTE MANDATORIA ----------------

--- main.c ---

• int open_files(char *input, char *output, int *fd_in, int *fd_out)
  Propósito: Abrir archivos de entrada y salida
  - Abre el archivo de entrada en modo lectura (O_RDONLY)
  - Si falla, usa /dev/null como entrada
  - Abre el archivo de salida en modo escritura (O_WRONLY | O_CREAT | O_TRUNC)
  - Si falla al abrir salida, cierra entrada y retorna 0
  Retorno: 1 si éxito, 0 si error

• int wait_end(pid_t pid1, pid_t pid2)
  Propósito: Esperar a que terminen ambos procesos hijos
  - Espera al primer proceso (pid1)
  - Espera al segundo proceso (pid2) y guarda su código de salida
  - Retorna el código de salida del último comando (como hace bash)
  Retorno: Código de salida del segundo proceso

• int init_pipe(int *pipe_fd, int fd_in, int fd_out)
  Propósito: Inicializar el pipe
  - Crea un pipe con pipe()
  - Si falla, cierra los descriptores de archivo y sale con error
  Retorno: 1 si éxito

• int main(int argc, char **argv)
  Propósito: Función principal
  - Verifica que haya exactamente 5 argumentos (programa + 4 args)
  - Abre archivos de entrada y salida
  - Crea un pipe
  - Crea dos procesos hijos para ejecutar cmd1 y cmd2
  - Cierra todos los descriptores de archivo en el padre
  - Espera a que terminen los hijos
  Retorno: Código de salida del último comando

--- child_process.c ---

• char **split_command(const char *command)
  Propósito: Dividir un comando en sus argumentos
  - Usa ft_split para separar por espacios
  - Maneja errores de malloc
  Retorno: Array de strings con los argumentos
  Nota: LIMITACIÓN - No maneja comillas, espacios en argumentos

• void exec_command(char **args, char *executable)
  Propósito: Ejecutar el comando con execve
  - Llama a execve con el ejecutable, argumentos y entorno
  - Si execve falla (solo retorna en caso de error), imprime error
  - Libera memoria y sale con código 127
  Nunca retorna (siempre ejecuta exit)

• void execute_child(const char *cmd, int input_fd, int output_fd)
  Propósito: Configurar y ejecutar un comando en proceso hijo
  - Redirige stdin al input_fd (si es diferente de STDIN_FILENO)
  - Redirige stdout al output_fd (si es diferente de STDOUT_FILENO)
  - Cierra los descriptores después de duplicarlos
  - Divide el comando en argumentos
  - Busca el ejecutable en PATH
  - Ejecuta el comando
  Nunca retorna (siempre ejecuta exit)

• pid_t create_child(const char *cmd, int in_fd, int out_fd, int close_fd)
  Propósito: Crear un proceso hijo
  - Hace fork()
  - En el hijo: cierra close_fd y ejecuta el comando
  - En el padre: retorna el PID del hijo
  Retorno: PID del proceso hijo (en el padre), no retorna en el hijo

--- find_executable.c ---

• char *get_path_env(void)
  Propósito: Obtener la variable de entorno PATH
  - Busca en la variable global environ
  - Busca la variable que comience con "PATH="
  - Retorna el valor después de "PATH=" (omite los primeros 5 caracteres)
  Retorno: String con PATH o NULL si no existe

• char *join_path(const char *dir, const char *command)
  Propósito: Concatenar un directorio y un comando
  - Calcula la longitud necesaria (dir + "/" + command + '\0')
  - Aloca memoria
  - Copia dir, añade "/", añade command
  Retorno: String con la ruta completa o NULL si falla malloc

• char *find_executable(char *command)
  Propósito: Buscar un ejecutable en PATH
  - Si el comando ya es un path válido (access X_OK), lo retorna
  - Obtiene PATH y lo divide en directorios
  - Prueba cada directorio concatenándolo con el comando
  - Verifica si el archivo existe y es ejecutable (access X_OK)
  - Si encuentra uno, retorna la ruta completa
  - Si no encuentra ninguno, retorna NULL
  Retorno: String con ruta completa del ejecutable o NULL

---------------- PARTE BONUS ----------------

--- main_bonus.c ---

• void init_pipex(t_pipex *data, int argc, char **argv)
  Propósito: Inicializar estructura de datos según modo (here_doc o normal)
  - Detecta si el primer argumento es "here_doc"
  - En modo here_doc:
    * Configura limiter, comandos y archivo de salida en modo append
    * Llama a handle_here_doc para leer input
    * Usa STDIN_FILENO como entrada
  - En modo normal:
    * Configura comandos, archivo entrada y salida normal
  - Calcula cantidad de comandos según argc

• void execute_pipeline(t_pipex *data)
  Propósito: Orquestar la ejecución de múltiples comandos con pipes
  - Crea N-1 pipes (donde N = cantidad de comandos)
  - Hace fork para cada comando
  - Cierra todos los pipes en el padre
  - Espera a que terminen todos los procesos
  - Libera memoria de los pipes

• int main(int argc, char **argv)
  Propósito: Función principal del bonus
  - Verifica mínimo 5 argumentos
  - Inicializa datos con init_pipex
  - Verifica que los archivos se abrieron correctamente
  - Ejecuta el pipeline
  - Cierra descriptores y retorna

--- child_process_bonus.c ---

• char **split_command(const char *command)
  Igual que en mandatory

• void exec_command(char **args, char *executable)
  Igual que en mandatory

• void execute_child(const char *cmd, int input_fd, int output_fd)
  Igual que en mandatory pero con cierre de descriptores mejorado

--- utils_bonus.c ---

• void error_exit(char *msg)
  Propósito: Imprimir error y salir
  - Escribe mensaje en stderr
  - Sale con código 1

• int open_file(char *file, int mode)
  Propósito: Abrir archivo según modo
  - mode 0: Lectura (O_RDONLY)
  - mode 1: Escritura truncando (O_WRONLY | O_CREAT | O_TRUNC)
  - mode 2: Escritura añadiendo (O_WRONLY | O_CREAT | O_APPEND)
  - Imprime error con perror si falla
  Retorno: Descriptor de archivo o -1 si error

• void handle_here_doc(char *limiter)
  Propósito: Implementar funcionalidad here_doc
  - Crea un pipe temporal
  - Lee líneas de stdin con get_next_line
  - Escribe cada línea en el pipe hasta encontrar el limiter
  - Cuando encuentra el limiter, cierra escritura del pipe
  - Redirige la lectura del pipe a stdin con dup2
  - Cierra el descriptor de lectura
  Resultado: stdin queda conectado al contenido leído

--- pipe_utils_bonus.c ---

• void close_pipes(int **pipes, int count)
  Propósito: Cerrar todos los pipes
  - Itera sobre todos los pipes
  - Cierra lectura y escritura de cada pipe

• int **create_pipes(int count)
  Propósito: Crear múltiples pipes
  - Aloca array de count punteros
  - Para cada uno, aloca array de 2 ints
  - Crea pipe con pipe()
  Retorno: Array bidimensional de descriptores

• void get_fds(t_pipex *data, int **pipes, int i, int *fds)
  Propósito: Determinar descriptores de entrada/salida para comando i
  - Si es el primer comando (i=0): entrada = infile
  - Si no: entrada = lectura del pipe anterior
  - Si es el último comando: salida = outfile
  - Si no: salida = escritura del pipe actual

• void close_unused_pipes(int **pipes, int count, int i)
  Propósito: Cerrar pipes no usados por el comando i
  - Cada proceso hijo solo necesita su entrada y salida
  - Cierra todos los demás descriptores
  - Esto previene que los procesos mantengan pipes abiertos innecesariamente

• void setup_pipes(t_pipex *data, int **pipes, int i)
  Propósito: Configurar pipes para el comando i y ejecutarlo
  - Obtiene los descriptores correctos con get_fds
  - Cierra pipes no necesarios
  - Ejecuta el comando con execute_child

--- process_bonus.c ---

• void fork_processes(t_pipex *data, int **pipes)
  Propósito: Crear procesos hijos para cada comando
  - Itera sobre todos los comandos
  - Hace fork para cada uno
  - En el hijo: configura pipes y ejecuta comando
  - En el padre: continúa al siguiente comando

• void wait_processes(int count)
  Propósito: Esperar a que terminen todos los procesos
  - Llama a wait() count veces
  - No guarda códigos de salida (simplificado)

• void free_pipes(int **pipes, int count)
  Propósito: Liberar memoria de los pipes
  - Libera cada array interno
  - Libera el array principal

--- find_executable_bonus.c ---
  Idéntico a la versión mandatory

5. FLUJO DE TRABAJO
================================================================================

---------------- MANDATORY ----------------

PASO 1: INICIALIZACIÓN
  main() recibe: ./pipex file1 "cmd1" "cmd2" file2
  ↓
  Verifica argc == 5
  ↓
  open_files() abre file1 (lectura) y file2 (escritura)
  ↓
  init_pipe() crea un pipe: pipe_fd[0] (lectura), pipe_fd[1] (escritura)

PASO 2: PRIMER PROCESO (CMD1)
  create_child(cmd1, file1_fd, pipe_fd[1], pipe_fd[0])
  ↓
  fork() → Proceso hijo
  ↓
  Cierra pipe_fd[0] (no necesita lectura del pipe)
  ↓
  execute_child()
    - dup2(file1_fd, STDIN) → stdin ahora lee de file1
    - dup2(pipe_fd[1], STDOUT) → stdout ahora escribe al pipe
    - Cierra descriptores originales
    - Busca y ejecuta cmd1
  ↓
  cmd1 lee de file1 y escribe al pipe

PASO 3: SEGUNDO PROCESO (CMD2)
  create_child(cmd2, pipe_fd[0], file2_fd, pipe_fd[1])
  ↓
  fork() → Proceso hijo
  ↓
  Cierra pipe_fd[1] (no necesita escritura al pipe)
  ↓
  execute_child()
    - dup2(pipe_fd[0], STDIN) → stdin ahora lee del pipe
    - dup2(file2_fd, STDOUT) → stdout ahora escribe a file2
    - Cierra descriptores originales
    - Busca y ejecuta cmd2
  ↓
  cmd2 lee del pipe y escribe a file2

PASO 4: PROCESO PADRE
  Cierra todos los descriptores (file1_fd, file2_fd, pipe_fd[0], pipe_fd[1])
  ↓
  wait_end() espera a ambos procesos
  ↓
  Retorna código de salida de cmd2

DIAGRAMA DE FLUJO DE DATOS:
  
  file1 → [cmd1] → pipe → [cmd2] → file2
  
  Proceso Padre: gestiona apertura/cierre y espera
  Proceso Hijo 1: ejecuta cmd1
  Proceso Hijo 2: ejecuta cmd2

---------------- BONUS: MÚLTIPLES PIPES ----------------

EJEMPLO: ./pipex file1 "cmd1" "cmd2" "cmd3" file2

PASO 1: INICIALIZACIÓN
  main_bonus() recibe argumentos
  ↓
  init_pipex() detecta modo normal
  - cmd_count = 3 (argc - 3)
  - cmd_args apunta a {"cmd1", "cmd2", "cmd3"}
  ↓
  create_pipes(2) crea 2 pipes:
  - pipes[0]: cmd1 → cmd2
  - pipes[1]: cmd2 → cmd3

PASO 2: CREACIÓN DE PROCESOS
  fork_processes() crea 3 procesos:
  
  Proceso 0 (cmd1):
    - Entrada: file1
    - Salida: pipes[0][1] (escritura)
    - Cierra: pipes[0][0], pipes[1][0], pipes[1][1]
  
  Proceso 1 (cmd2):
    - Entrada: pipes[0][0] (lectura)
    - Salida: pipes[1][1] (escritura)
    - Cierra: pipes[0][1], pipes[1][0]
  
  Proceso 2 (cmd3):
    - Entrada: pipes[1][0] (lectura)
    - Salida: file2
    - Cierra: pipes[0][0], pipes[0][1], pipes[1][1]

PASO 3: EJECUCIÓN Y ESPERA
  Padre cierra todos los pipes
  ↓
  wait_processes() espera a los 3 procesos
  ↓
  free_pipes() libera memoria

DIAGRAMA:
  file1 → [cmd1] → pipe0 → [cmd2] → pipe1 → [cmd3] → file2

---------------- BONUS: HERE_DOC ----------------

EJEMPLO: ./pipex here_doc EOF "grep hello" "wc -l" outfile

PASO 1: DETECCIÓN
  init_pipex() detecta "here_doc" en argv[1]
  ↓
  - limiter = "EOF"
  - outfile en modo APPEND (O_APPEND)

PASO 2: LECTURA DE STDIN
  handle_here_doc("EOF")
  ↓
  Crea pipe temporal
  ↓
  Bucle:
    Muestra prompt "> "
    Lee línea con get_next_line
    Si línea == "EOF\n" → break
    Escribe línea al pipe
  ↓
  Cierra escritura del pipe
  ↓
  dup2(pipe_read, STDIN) → stdin ahora lee del pipe

PASO 3: EJECUCIÓN NORMAL
  Igual que múltiples pipes, pero:
  - Primer comando lee de stdin (que está conectado al pipe temporal)
  - Último comando escribe en append mode

DIAGRAMA:
  stdin → [usuario escribe hasta EOF] → pipe_temp → [cmd1] → pipe → [cmd2] >> outfile

6. PREGUNTAS FRECUENTES (FAQ)
================================================================================

Q1: ¿Por qué usamos fork()?
A1: fork() crea un proceso hijo que es una copia exacta del padre. Esto nos
    permite ejecutar dos programas diferentes simultáneamente. Sin fork(),
    execve() reemplazaría completamente nuestro programa.

Q2: ¿Por qué usamos dup2()?
A2: dup2() duplica un descriptor de archivo. Lo usamos para redirigir stdin/
    stdout. Cuando hacemos dup2(fd, STDIN_FILENO), cualquier lectura de stdin
    ahora leerá de fd en lugar del teclado.

Q3: ¿Por qué cerramos tantos descriptores?
A3: Cada descriptor de archivo abierto consume recursos. Si no los cerramos:
    - Los pipes no se cerrarán completamente → los comandos pueden bloquearse
    - Memory leaks → el sistema operativo mantiene recursos abiertos
    - Alcanzar límite de descriptores abiertos

Q4: ¿Qué pasa si cmd1 falla pero cmd2 funciona?
A4: cmd2 se ejecutará de todas formas. Leerá del pipe (que estará vacío o con
    datos parciales) y producirá su salida. El código de salida final será el
    de cmd2, no el de cmd1.

Q5: ¿Por qué el padre espera a los hijos?
A5: Si el padre termina antes que los hijos, los procesos hijos se convierten
    en "zombies". waitpid() evita esto y permite al padre obtener el código
    de salida de los hijos.

Q6: ¿Cómo funcionan los pipes internamente?
A6: Un pipe es un buffer en memoria del kernel. pipe() crea dos descriptores:
    - pipe[0]: lectura → lee datos del buffer
    - pipe[1]: escritura → escribe datos al buffer
    Los datos escritos en pipe[1] pueden leerse desde pipe[0].

Q7: ¿Por qué usamos access() en find_executable?
A7: access(path, X_OK) verifica si:
    - El archivo existe
    - Es ejecutable
    - El usuario tiene permisos de ejecución
    Retorna 0 si todas las condiciones se cumplen.

Q8: ¿Qué es environ?
A8: environ es una variable global que contiene todas las variables de entorno
    del proceso (PATH, HOME, USER, etc.). Es un array de strings terminado en
    NULL. execve() necesita el entorno para funcionar correctamente.

Q9: ¿Por qué split_command() no maneja comillas?
A9: Es una simplificación del proyecto. Un parser completo de shell es mucho
    más complejo. Por eso los comandos deben pasarse entre comillas dobles al
    invocar pipex: ./pipex file "ls -l" "wc" file2

Q10: ¿Cuál es la diferencia entre O_TRUNC y O_APPEND?
A10: - O_TRUNC: Trunca el archivo (lo vacía) antes de escribir
     - O_APPEND: Añade al final del archivo sin borrar contenido previo
     En modo normal usamos O_TRUNC (como > en bash)
     En here_doc usamos O_APPEND (como >> en bash)

Q11: ¿Por qué /dev/null si falla el archivo de entrada?
A11: Es para simular el comportamiento de bash. Si el archivo no existe, bash
     sigue ejecutando los comandos pero con entrada vacía. /dev/null siempre
     retorna EOF al leer (entrada vacía).

Q12: ¿Qué pasa si PATH no existe?
A12: find_executable() retornará NULL y el comando fallará con "command not
     found". Esto puede pasar en entornos muy restrictivos.

Q13: ¿Por qué exitcode 127 para comandos no encontrados?
A13: Es una convención de Unix/Linux:
     - 0: éxito
     - 1-125: errores generales
     - 126: comando encontrado pero no ejecutable
     - 127: comando no encontrado
     - 128+: terminado por señal

Q14: ¿Cómo manejar comandos con rutas absolutas?
A14: find_executable() primero verifica si el comando ya es un path válido con
     access(). Así ./pipex file "/bin/ls" "wc" file2 funcionará correctamente.

Q15: ¿Se puede usar pipex con comandos que no están en PATH?
A15: Sí, si proporcionas la ruta completa: ./pipex in "/ruta/completa/cmd" ...

Q16: ¿Por qué heredamos el entorno completo en execve?
A16: Algunos comandos necesitan variables de entorno (PATH, HOME, LANG, etc.)
     para funcionar correctamente. Pasar environ asegura que funcionen igual
     que si se ejecutaran desde shell.

Q17: Diferencia entre get_next_line en here_doc y read()?
A17: get_next_line() lee línea por línea, lo cual es perfecto para here_doc
     que necesita detectar el limiter. read() lee bloques de bytes arbitrarios.

Q18: ¿Qué mejoras se podrían hacer?
A18: - Parser de comandos que maneje comillas, escapes, variables
     - Manejo de señales (Ctrl+C, Ctrl+Z)
     - Redirecciones múltiples (>, <, >>)
     - Wildcards (*, ?)
     - Subshells y operadores lógicos (&&, ||)
     - Built-ins de shell (cd, export, etc.)
     Pero todo eso está fuera del alcance de pipex.
